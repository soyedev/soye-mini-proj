# 1. 서비스 선정

## 1.1 어떤 서비스의 장애를 자동 복구할 것인가?

**서비스 이름:** 서울 청년 주거지원 비교·이사 체크리스트

**한 문장 설명:** 서울에 거주하는 청년이 가상 프로필과 이사 예정일을 입력하면, 서비스는 모의 정책 자료를 비교하고 서류·일정 안내 및 공식 출처 링크를 반환한다.

> 사용자가 **가상 프로필과 이사 예정일**을 요청하면, 서비스는 **주거지원 정책 비교와 일정·서류 안내**를 수행하고 **가능성·정보 부족·조건 불일치 상태, 체크리스트, 공식 출처 링크**를 반환한다.

**정상 실행 흐름:**

```text
사용자
  ↓
[프로필·이사 예정일 입력]
  ↓
[모의 정책 검색·조건 비교]
  ↓
[서류·일정 및 이사 체크리스트 생성]
  ↓
정상 결과: [정책 3개, 기준일·접수 상태·출처, 안내 상태와 체크리스트]
```

**핵심 의존 서비스:**

| 의존 대상 | 용도 | 실패 시 영향 | 모의 구현 여부 |
|---|---|---|---|
| 정책 검색 기능 | 예시 정책 3개 검색·비교 | 정책 비교가 지연되거나 표시되지 않음 | 예 |
| 일정·체크리스트 기능 | 서류·신청 일정과 제한된 이사 항목 제공·저장 | 일정 안내가 누락되거나 저장 상태를 확인할 수 없음 | 예; 상태 저장은 PostgreSQL 사용 |
| PostgreSQL | 사건 타임라인과 체크리스트 상태 저장, 멱등 상태 확인 | 기록·기존 상태를 확인할 수 없으면 안전 중단 및 안내 | 로컬 실습용; 네 번째 장애 시나리오로 연결·쓰기 실패 주입 |

## 1.2 서비스가 멈추면 어떤 영향이 발생하는가?

### 사용자 영향

- 정책 비교 또는 서류·일정 안내를 받지 못하거나 지연된다.
- 복구할 수 없으면 공식 정책 페이지에서 직접 확인해야 한다.

### 운영 영향

- 장애 유형·근거·시도 이력·검증 결과를 확인하고 수동으로 안내해야 한다.
- 실제 운영 서비스가 아니므로 기존 수동 대응 이력은 해당 없음; 실습용 대응 절차를 재현한다.

### 데이터·비용·보안 영향

- 가상 프로필만 사용하며 정확한 소득액·계약서 원문·인증정보는 받거나 저장하지 않는다.
- 모의 정책 자료는 출처·기준일을 포함한 읽기 전용 JSON이며 정책 검색은 읽기 전용이다.
- 일정 상태가 불명확하면 중복 생성 방지를 위해 멈춘다. 실제 결제·신청·외부 알림은 없다.

### 심각도

- [ ] 낮음 — 지연되지만 핵심 기능은 유지됨
- [x] 중간 — 일부 요청이 실패하고 운영자 대응이 필요함
- [ ] 높음 — 핵심 기능이 중단되거나 데이터·금전 피해 가능

**선택 근거:** 안내 기능은 멈출 수 있지만 실제 신청·결제·운영 데이터 처리는 없으며, 사용자는 공식 출처에서 직접 확인할 수 있다.

## 1.3 현재 사람은 장애를 어떻게 발견하고 복구하는가?

| 단계 | 현재 사람의 행동 | 사용하는 정보·도구 | 소요시간 | 문제점 |
|---|---|---|---:|---|
| 탐지 | 실습에서는 모의 오류·타임아웃·연결 실패 신호를 확인 | 헬스체크, 응답 결과, 사건 로그 | [미결정] | 운영 중인 서비스가 없어 실제 탐지 이력 없음 |
| 진단 | 신호와 근거를 사전 정의한 유형에 대응 | 오류 코드, 타임아웃, 의존 기능 상태 | [미결정] | 근거가 없거나 상충하면 Unknown 처리 필요 |
| 복구 | 허용된 모의 기능 재시도; 상한 도달 시 중단 | 사건 기록, 회로 상태 | 최대 재시도 대기 간격 합계 약 8.5초(+지터), 실행시간 [미결정] | 실제 수동 운영 절차는 [해당 없음] |
| 검증 | 별도 역할이 헬스체크·핵심 기능·멱등 상태 확인 | 읽기 전용 상태·테스트 결과 | [미결정] | 복구 담당자 자기보고만으로 완료 처리하면 안 됨 |
| 보고 | 최종 상태와 공식 링크를 사용자에게 안내 | 사건 타임라인, 승인 문구 | [미결정] | 저장·알림 실패 시 수동 확인 경로 필요 |

**자동화하려는 단계:** 신호 감지·기록, 고정 규칙 기반 분류, 제한된 재시도, 회로 차단·재개 확인, 독립 검증, 실패 안내.

**사람이 계속 담당해야 할 단계:** Unknown·근거 충돌·확인 불가 상황 판단, 정책 자료/규칙 변경 승인, 실제 외부 연동이나 운영 영향이 있는 행동의 승인.

## 1.4 3일 동안 재현 가능한 최소 서비스는 무엇인가?

### 포함 범위

- 출처·기준일·접수 상태를 표시하는 예시 정책 3개 비교
- 가상 프로필에 대한 가능성·정보 부족·조건 불일치 안내
- 제도별 서류·일정과 전입신고·확정일자·보증보험 중 최대 3개 일반 체크 항목

- PostgreSQL 사건 타임라인과 체크리스트 상태 저장; 정책 자료는 읽기 전용 JSON

### 제외 범위

- 개인정보·계약서 업로드, 실제 정부 API 신청·제출, 외부 알림 발송
- 임의 쉘/SQL 실행, DB 직접 쓰기, 데이터 삭제, 임의 서비스 조작
- 법률 자문 및 개인별 법정 기한 산정

# 2. 에이전트 설계

## 2.1 장애를 탐지하는 주체는 누구인가?

**에이전트 이름:** Monitor (규칙/함수 역할; 별도 LLM 여부 미정)

**관찰 데이터:**

- [x] 헬스체크 응답
- [x] 애플리케이션 로그
- [x] 오류율: 사건별 실패 신호; 별도 집계 임계값은 [미결정]
- [x] 응답시간 및 타임아웃 신호
- [ ] 프로세스 상태
- [x] 기타: 의존 기능 연결 결과, 사건·추적 ID

**장애 판정 조건:** 사전 정의한 HTTP 5xx, 요청 타임아웃, 연결 실패/결과 부재 신호를 관찰하면 사건을 생성한다. 감시 자체에 실패하면 자동 복구를 시작하지 않고 알린다.

**출력 메시지:** 사건 ID, 의존 기능, 관찰 신호·근거 참조, 발생 시각, 심각도(중간), 초기 상태.

## 2.2 원인을 진단하는 주체는 누구인가?

**에이전트 이름:** Diagnosis (고정 신호 매핑; 모델은 근거 후보 설명만 가능)

**입력:** Monitor 사건 신호와 근거 참조, 의존 기능, 시각 및 이전 시도 기록.

**분류할 장애 유형:**

| 장애 코드 | 설명 | 판단 근거 | 신뢰도 또는 규칙 |
|---|---|---|---|
| HTTP_5XX | 모의 정책 검색 서버 오류 | HTTP 응답 코드가 5xx | 고정 코드 매핑; 자동 재시도 허용 |
| TIMEOUT | 정책 검색이 요청 제한시간 안에 응답하지 않음 | 3초 타임아웃 신호 | 고정 타임아웃 매핑; 정책 검색 요청 제한은 3초 |
| DEPENDENCY_UNAVAILABLE | 일정 기능 연결 실패 또는 결과 부재 | 연결 오류/필수 결과 없음 | 고정 신호 매핑; 상태 불명확 시 변경 중단 |
| DATABASE_UNAVAILABLE | PostgreSQL 연결 또는 쓰기 실패 | 연결 오류/기록 실패/멱등 상태 조회 실패 | 고정 신호 매핑; 쓰기 상태를 확인할 수 없으면 재시도 중단·에스컬레이션 |
| UNKNOWN | 미등록, 근거 누락 또는 상충 | 알려진 신호에 매핑 불가 | 자동 변경 금지, 사람에게 에스컬레이션 |

**원인을 판단할 수 없을 때 행동:** 복구를 실행하지 않고 `Unknown`으로 기록한 뒤 근거와 함께 에스컬레이션한다.

## 2.3 복구를 실행하는 주체는 누구인가?

**에이전트 이름:** Recovery (허용목록 기반 애플리케이션 기능)

**허용된 복구 행동:**

- 동일 사건·의존 기능별로 최초 호출 포함 최대 4회 호출(추가 재시도 3회)
- 지수형 대기와 ±20% 무작위 지연: 명목 간격 1초, 2.5초, 5초
- 일정 재시도 시 동일 멱등 키 항목 재사용 또는 갱신
- 회로 개방 중 호출 중단, 냉각 20초 후 half-open 상태 확인 1회

**금지된 행동:**

- 임의 쉘 명령, SQL 실행, PostgreSQL 직접 쓰기
- 실제 정부 사이트 조작·신청, 외부 알림 발송, 정책/운영 규칙 변경
- 상태가 불명확한 일정의 재생성·삭제, 허용목록 밖 복구

**필요한 도구·API·명령:** 허용목록에 등록된 모의 정책 검색·일정 기능 호출, 고정 애플리케이션 저장 기능, 사건 상태 기록 기능. 구체 API·명령은 [미결정].

## 2.4 복구 성공을 독립적으로 검증하는 주체는 누구인가?

**에이전트 이름:** Verification (읽기 전용 독립 역할)

**독립성이 필요한 이유:** Recovery의 성공 보고만으로 사건을 종료하지 않고 별도 신호·핵심 기능 결과로 실제 정상화를 확인한다.

**검증 항목:**

- [x] 헬스체크 정상
- [x] 핵심 기능 테스트 통과
- [ ] 오류율 정상 범위 (수치 임계값 [미결정])
- [ ] 응답시간 정상 범위 (전체 서비스 SLA와 역할별 요청 타임아웃 [미결정]; 모의 정책 검색은 3초)
- [x] 데이터 무결성 확인 (멱등 키별 일정 항목 정확히 하나)
- [x] 회귀 테스트 통과 (실습 범위에서 정의할 핵심 시나리오)

**복구 실패 판정 조건:** 검증 실패·시간 초과·상태 조회 불가, 또는 핵심 결과/멱등 상태 불일치. 실패 시 성공으로 표시하지 않고 사건을 유지하며 사용자 안내 또는 에스컬레이션한다.

## 2.5 오케스트레이터가 필요한가?

- [x] 필요함
- [ ] 필요하지 않음

**판단 근거:** 탐지·진단·복구·검증·알림 순서, 사건별 상태, 재시도 상한, 회로 상태와 에스컬레이션을 일관되게 통제해야 한다.

### 오케스트레이터의 책임

- 정해진 상태 흐름에 따라 역할을 호출하고 사건·시도·타임라인을 관리
- 의존 기능별 재시도 상한과 회로 차단/냉각/half-open을 적용
- 검증 전 완료 처리 금지, 실패·Unknown·상태 불명 시 안전 중단과 안내

### 오케스트레이터가 해서는 안 되는 일

- 허용 정책을 우회하거나 모델 출력만으로 복구 행동을 만들어 실행
- 독립 검증 생략, 상태 불명 일정 재생성, 임의 DB·쉘 조작

## 2.6 에이전트 협업 구조

| 에이전트 | 입력 | 출력 | 호출 주체 | 허용 권한 | 타임아웃 |
|---|---|---|---|---|---:|
| Monitor | 헬스체크·기능 응답·로그 | 사건 신호 및 근거 | 서비스/정해진 감시 루프 | 읽기, 사건 기록 | [미결정] |
| Diagnosis | 신호·사건 근거 | 유형 후보·근거 또는 Unknown | Orchestrator | 근거 조회, 분류 출력 | [미결정] |
| Recovery | 승인된 작업 ID·사건·시도 번호 | 실행 결과 | Orchestrator | 허용된 모의 기능 호출 | 역할별 타임아웃 [미결정]; 모의 정책 검색 호출은 3초 |
| Verification | 독립 헬스체크·기능·저장 상태 | 성공/실패 및 근거 | Orchestrator | 읽기 전용 확인 | [미결정] |
| Notification | 최종 상태·검증 결과·공식 출처 | 사용자 안내 | Orchestrator | 승인 문구 전달 | [미결정] |

### 협업 흐름

```text
[장애 발생]
  ↓
[Monitor가 신호·사건 기록]
  ↓
```

## 5.2 장애 탐지부터 복구까지 걸린 시간을 어떻게 측정할 것인가?

```text
injected_at  = 장애 주입 시각
 detected_at = Monitor가 사건을 생성한 시각
recovery_started_at = 첫 복구 호출 시각
recovered_at = Verification 성공 시각 (실패/에스컬레이션이면 해당 종결 시각 별도 기록)
```

```text
MTTD = detected_at - injected_at
MTTR = recovered_at - injected_at
복구 실행시간 = recovered_at - recovery_started_at
```

**시연 목표:** 일반 장애 MTTD ≤5초, MTTR ≤15초. 전체 워크플로 제한은 30초, 역할별 호출 제한은 3초다. 초과 시 현재 요청을 안전 중단하고, 회로 차단은 20초 냉각 후 별도 half-open 확인 결과를 기록한다. 전체 사용자 응답 SLA는 별도 목표 없이 측정만 한다.

**시간을 기록할 컴포넌트:** 사건 상태·타임라인을 관리하는 애플리케이션/Orchestrator; PostgreSQL에 저장.

**시간 형식과 타임존:** ISO 8601 타임스탬프와 UTC 권장; 화면 표시 시간대는 [미결정].

## 구현하지 않을 것

1. 실제 개인정보·계약서 처리 및 확정적인 자격 판정·법률 자문.
2. 실제 신청·제출, 외부 알림, 운영 정책 변경 또는 실제 서비스 복구.
3. 임의 쉘/SQL 실행, PostgreSQL 직접 쓰기, 불명확한 상태에서의 삭제·재생성.

## 성공 기준

1. 정상 요청에서 정책 3개와 기준일·접수 상태·공식 출처, 가상 프로필 상태, 일정·최대 3개 체크 항목을 표시한다.
2. 네 장애 유형(HTTP 5xx, 3초 타임아웃, 일정 기능 연결 실패, PostgreSQL 연결·쓰기 실패)이 각각 기록되고 독립 검증을 통과하거나, 재시도 상한 내 복구 실패 후 안전 안내된다.
3. 반복 실패에서 회로가 열리고 20초 후 half-open 결과가 기록되며, 재시도 뒤 멱등 키별 일정 항목은 하나만 남는다.
