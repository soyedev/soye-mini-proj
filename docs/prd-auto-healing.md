# PRD: 서울 청년 주거지원 비교·이사 체크리스트 자가 치유 서비스

## 1. 문서 정보

- 작성자: 전소예 (1인 프로젝트)
- 작성일: 2026-10-29
- 상태: 사용자 승인 완료 — 작업목록 상위 작업 검토 대기
- 기준 문서: `prompts/01-create-prd.md`, `references/01-practice-guide.md`
- 관련 아이디에이션: [`ideation-worksheet.md`](ideation-worksheet.md)

## 2. 프로젝트 개요

서울 거주 청년이 가상 프로필과 이사 예정일을 바탕으로 주거지원 제도 세 가지의 기본 조건·접수 상태·공식 출처를 비교하고, 관련 일정 및 체크리스트를 확인하는 실습용 서비스다. 서비스는 정책 검색, 일정 처리, PostgreSQL 저장에서 발생하는 장애를 탐지하고, 사전 허용된 범위에서만 제한적으로 재시도한다. 복구 완료는 별도 검증기가 확인해야 하며, 확인할 수 없는 상태는 성공으로 표시하지 않는다.

## 3. 해결할 문제와 경계

### 사용자 문제

청년 주거지원 제도는 조건과 접수 기간, 증빙 서류가 서로 다르다. 사용자는 자신에게 적용될 수 있는 제도와 다음 행동을 비교하기 어렵고, 정책 데이터나 일정 기능이 실패하면 안내가 끊길 수 있다.

### 정상 흐름

사용자가 가상 프로필과 이사 날짜를 입력하면 서비스가 세 제도를 출처·기준일·접수 상태와 함께 비교하고, 확정 판정 대신 `가능성 있음`, `조건 불일치`, `정보 부족` 중 하나와 근거를 제시한 뒤 체크리스트와 진행 상태를 저장한다.

### 서비스 경계

- 대상은 서울 청년 주거지원 정보 비교의 3일 학습용 MVP다.
- 모든 서울 자치구·제도·예외 조건을 포괄하지 않는다.
- 실제 신청·제출, 법률 판단, 확정적인 수급 자격 판정, 실제 복구 작업은 수행하지 않는다.
- 장애 복구는 로컬 모의 의존 기능에만 적용한다.

## 4. 사용자와 이해관계자

| 사용자/역할 | 필요 | 경계 |
|---|---|---|
| 서울 청년 사용자 | 제도 조건과 다음 준비 항목을 이해 | 결과는 참고 정보이며 공식 기관의 최종 판단을 대체하지 않음 |
| 개발자/시연자 | 장애 탐지·복구·검증 과정을 재현하고 설명 | 모의 정책·가상 프로필만 사용 |
| 문서 검토자/승인자 | 범위·안전 통제·성공 증거 검토 | 검토자: 전소예; 최종 승인일은 승인 시 기록 |

## 5. 목표와 성공 기준

### 제품 목표

1. 정책 3개를 기준일·접수 상태·공식 출처와 함께 비교한다.
2. 정책 조건 비교와 자격 가능성 안내를 안전하게 제공한다.
3. 서류·이사 일정 체크 항목을 제공하고 진행 상태를 저장한다.
4. 네 가지 장애를 재현하고, 제한 복구·독립 검증 또는 안전 중단을 사건 기록으로 증명한다.

### 측정 가능한 완료 기준

- 정상 시나리오에서 정책 3개, 공식 출처, 기준일, 접수 상태, 판정 상태 및 최대 3개의 체크 항목이 표시된다.
- 네 장애 유형(정책 HTTP 5xx, 정책 검색 3초 타임아웃, 일정 의존 기능 연결 실패, PostgreSQL 연결·쓰기 실패)이 각각 사건 타임라인에 기록된다.
- 복구 성공은 복구 담당자와 분리된 읽기 전용 검증의 성공 결과가 있을 때만 선언된다.
- 실패·Unknown·저장 상태 불명 시 성공 안내가 없고, 사용자에게 수동 확인 또는 공식 출처 경로가 제공된다.
- 동일 일정 멱등 키는 최종 상태에서 최대 한 건만 존재한다.
- 재시도 횟수, 대기, 회로 상태 전이, 검증 결과 및 최종 상태를 PostgreSQL 타임라인에서 추적할 수 있다.
- 일반 장애 시연 목표는 MTTD 5초 이내, MTTR 15초 이내다. 회로 차단 시나리오는 20초 냉각 후 별도 half-open 확인 결과를 기록한다. 전체 사용자 응답 SLA는 별도 목표 없이 측정만 한다.

## 6. 비목표

- 실제 개인의 정확한 소득·자산·계약서 원문·인증정보 수집
- 수급 자격의 확정 판정, 법률 자문 또는 법정 기한 산정
- 실제 정부24·LH·HUG 신청/제출, 외부 알림 또는 계정 연동
- 정책 원문을 자동으로 변경하거나 사용자 대신 정책 결정을 내리는 행위
- 임의 쉘 명령, 임의 SQL, PostgreSQL 직접 쓰기 또는 미승인 도구 호출
- 장애 복구를 위한 데이터 삭제·임의 재생성·운영 서비스 변경

## 7. 정상 서비스 시나리오

1. 사용자는 실제 개인정보 대신 합성 프로필 필드(나이 구간, 서울 거주 여부, 가구 형태, 소득 구간, 무주택 여부, 보증금·월세 구간, 이사 예정일)를 제공한다.
2. 정책 검색기는 로컬 읽기 전용 JSON에서 예시 제도 세 건을 가져온다. 각 항목에는 공식 출처 URL과 확인 기준일이 붙는다.
3. 자격 비교기는 버전이 지정된 결정적 규칙으로 입력값을 비교한다. 필요한 입력이 빠지거나 정책 규칙·원문이 충돌하면 `정보 부족`을 반환하고 확정 판정을 금한다.
4. 설명 역할은 규칙이 산출한 결과와 인용 가능한 근거를 쉬운 말로 바꾼다. 모델은 자격 결과나 정책 규칙을 새로 결정하지 않는다.
5. 체크리스트 기능은 관련 서류와 최대 세 개의 일정 항목을 만든다. 중복 키는 `시나리오+제도+일정 종류+날짜`로 결정한다.
6. PostgreSQL에 사건 타임라인과 체크리스트 상태를 저장한다. 사용자는 상태·다음 행동·공식 링크를 확인한다.

### 합성 데모 프로필

테스트 전용 가상 사례: 만 24세, 서울 거주, 1인 미혼 가구, 무주택, 중위소득 55% 구간, 보증금 500만 원, 월세 40만 원, 이사 예정일 2026-11-15. 정확한 소득액은 쓰지 않는다. 원가구 소득·자산 등 빠진 정보는 추정하지 않고 `정보 부족`으로 표시한다. 이 프로필은 실제 자격 판정에 사용할 수 없다.

정책 데이터 예시는 2026-10-28에 확인한 공식 페이지의 서울 청년월세지원, 청년월세 지원, LH 청년 전세임대 공고를 사용한다. 접수 기간과 공고는 바뀌므로 시연 시 원문과 정정 공지를 재확인하고, 과거 접수 상태를 현재 접수 중으로 표현하지 않는다.

## 8. 장애 시나리오

| ID | 장애 | 탐지 근거 | 안전한 처리 |
|---|---|---|---|
| F-01 | 정책 검색 HTTP 5xx | 응답 코드, trace/incident ID | 정책 검색 의존 기능의 상한 내 재시도; 실패하면 캐시 기준일을 명시하거나 공식 링크 안내 |
| F-02 | 정책 검색 타임아웃 | 3초 요청 제한 초과 | 상한 내 재시도; 초과 결과를 성공으로 간주하지 않음 |
| F-03 | 일정 의존 기능 연결 실패 또는 결과 부재 | 연결 오류·필수 결과 누락 | 멱등 상태를 먼저 조회; 상태 불명 시 추가 쓰기를 멈추고 수동 체크리스트 안내 |
| F-04 | PostgreSQL 연결·쓰기 실패 | 연결 오류·커밋 결과 불명 | 커밋 전 실패가 확인된 경우만 제한 재시도; 결과 불명은 멱등 키 조회, 조회 불가면 안전 중단·에스컬레이션 |

같은 장애가 최초 요청과 추가 재시도 모두에서 반복되는 것은 별도 장애 종류가 아니라 회로 차단 시연 조건이다.

## 9. 에이전트 구성과 권한

| 역할 | 입력 | 출력 | 허용 권한 | 금지 행동 |
|---|---|---|---|---|
| Monitor | 헬스체크, 응답 코드, 의존 기능 상태 | 사건 신호·관측 근거 | 읽기, 제한된 사건 기록 요청 | 근거 없는 사건 생성 또는 복구 실행 |
| Diagnosis | 사건 신호, 코드화된 오류, 정책/기능 상태 | 장애 유형 후보와 근거 또는 `UNKNOWN` | 읽기 전용 근거 조회, 제한 스키마 출력 | 복구 실행, 정책 조건 추측, 근거 없는 분류 |
| Recovery | Orchestrator가 발급한 허용 작업 ID, incident ID, 시도 번호 | 모의 기능 호출 결과 | allowlist에 있는 모의 호출만 | 임의 도구·쉘·SQL, 직접 DB 변경, 승인 없는 외부 호출 |
| Verification | 복구 전후 헬스체크, 핵심 결과, DB의 읽기 전용 상태 | 독립 성공/실패와 증거 | 읽기 전용 확인 | 복구 결과를 그대로 신뢰하거나 상태 불명에서 성공 선언 |
| Notification | 검증된 최종 상태, 근거, 공식 URL | 사전 정의된 사용자 안내 | 허용 템플릿의 문구 전달 | 자격 확정, 근거 없는 보장, 실제 신청·제출 |
| Orchestrator | 사건 상태, 고정 정책, 위 역할의 구조화 출력 | 호출 순서, 시도 제한, 종료·에스컬레이션 | 결정적 상태기계와 allowlist 제어 | 모델 출력으로 한도·권한·규칙 변경 |

에이전트는 책임 경계를 설명하기 위한 논리 역할이다. 핵심 판정·권한 검사는 고정 코드와 스키마 검증이 맡으며, LLM을 쓰더라도 설명 문구 작성에만 제한한다.

## 10. 협업 흐름과 상태 전이

```text
요청 → 입력 스키마 검증 → 정책 JSON 읽기 → 결정적 자격 비교
  → 체크리스트 계산 → PostgreSQL 저장 → 독립 검증 → 결과 안내
                         ↘ 장애 감지 → 진단(Unknown 가능)
                           → 허용 복구/제한 재시도 → 독립 검증
                             → 성공 종료 또는 안전 중단·에스컬레이션
```

사건 상태는 `DETECTED → DIAGNOSED → RECOVERING → VERIFYING → RECOVERED` 또는 `SAFE_STOP / ESCALATED`로 전이한다. 허용되지 않은 전이는 거부한다. `UNKNOWN`, 근거 상충, 필수 근거 부재, 검증 실패는 복구 완료로 전이할 수 없다.

## 11. 복구 정책

### 재시도와 회로 차단

- 최대 호출 4회: 최초 1회 + 추가 재시도 3회.
- 대기: 지수 백오프 1초, 2.5초, 5초에 각각 ±20% 지터.
- 모의 정책 검색 호출 타임아웃: 3초.
- 같은 의존 기능에서 같은 사건의 네 호출이 모두 실패하면 해당 기능 회로를 연다. 다른 사건이나 다른 기능의 실패를 합산하지 않는다.
- 회로 냉각 시간: 20초. 이후 half-open 확인은 1회만 허용한다. 성공 시 닫고 실패 시 열린 상태를 유지하며 에스컬레이션한다.
- 20초는 시연용 기준값이며 운영값으로 해석하지 않는다.
- 전체 워크플로 벽시계 제한은 30초다. 이 안에 복구·검증이 끝나지 않으면 현재 요청을 `SAFE_STOP`으로 종료하며 성공으로 표시하지 않는다. 회로가 열린 경우 20초 냉각 후 half-open 확인은 별도 제한 호출로 실행하고 그 결과를 같은 사건 타임라인에 연결한다. 원래 요청을 30초 넘게 붙잡지 않는다.
- 각 역할 호출 제한은 3초다. 한 역할의 시간 초과는 실패로 기록하며, 재시도는 남은 30초 예산과 시도 상한 안에서만 허용한다.

### 멱등성과 저장 실패

- 일정 멱등 키는 `scenario_id + policy_id + item_type + due_date`로 만든다.
- 기존 항목을 읽어 재사용하거나 허용된 upsert만 한다. 키 충돌 또는 상태 조회 불가 시 쓰기를 중지한다.
- PostgreSQL 오류 후 커밋 전 실패가 확정된 경우만 재시도한다. 커밋 여부가 불명확하면 먼저 키로 읽기 확인하며, 확인할 수 없으면 재시도·중복 저장·성공 안내를 금지한다.
- 삭제/재생성 롤백은 허용하지 않는다. 안전 중단 후 사람이 상태를 확인한다.

## 12. 자율 실행·사람 승인·금지 기준

| 구분 | 기준 |
|---|---|
| 자동 실행 허용 | 읽기 전용 조회, 검증된 필드 비교, 허용된 모의 의존 기능 재시도, 회로 상태 전이, 동일 멱등 키 확인, 독립 읽기 검증 |
| 사람 승인 필요 | 정책 규칙·정책 데이터 변경, 새로운 복구 작업/도구 추가, 실제 외부 서비스 호출·신청·알림, MVP 범위 밖 데이터 변경 |
| 실행 금지 | 임의 셸·SQL, DB 직접 쓰기, 사용자 대신 실제 신청·제출, 확정 자격 보장, 불명확한 상태의 삭제·재생성, 회로·시도 상한 우회 |

MVP에는 승인 UI가 없다. 따라서 승인 필요한 행동은 실행하지 않고 공식 수동 경로를 안내한다. 사람 승인이 승인 기준을 대체하더라도 독립 검증과 기록은 생략할 수 없다.

### AI 판단 차단 장치

1. 제도 자격 결과는 버전 관리되는 결정적 규칙에서만 산출한다.
2. 모델 입력은 필요한 최소 필드로 제한하고, 출력은 고정 JSON 스키마와 enum 검증을 통과해야 한다.
3. 누락·충돌·신뢰 불가 출처는 `정보 부족` 또는 `UNKNOWN`으로 처리한다.
4. 정책 페이지와 JSON 원문은 신뢰할 수 없는 데이터다. 그 안의 문장을 시스템 지시나 도구 권한으로 실행하지 않는다.
5. 모델은 도구 목록, SQL, 재시도 횟수, 차단 시간, 정책 규칙을 변경할 수 없다.
6. Orchestrator만 allowlist 작업 ID를 호출한다. 모델은 SQL/DB/셸/정부 사이트에 직접 접근하지 않는다.
7. 모든 결과에 정책 출처·기준일·사용 규칙 버전·판정 근거 코드를 남기고, 독립 검증 전에는 성공을 표시하지 않는다.

## 13. 기능 요구사항

### FR-01 핵심: 정책 비교와 제한된 자격 안내

- 세 가지 예시 정책을 정책명, 기본 조건, 접수 상태, 기준일, 공식 출처 URL과 함께 제시한다.
- 합성 프로필과 버전 지정 규칙으로 비교해 `가능성 있음`, `조건 불일치`, `정보 부족` 상태를 반환한다.
- 필요한 조건이 제공되지 않으면 추정하거나 확정하지 않는다.
- 정책 검색 실패 시 신선한 정보인 것처럼 꾸미지 않으며 기준일·실패 상태·공식 확인 경로를 표시한다.

### FR-02 지원: 서류·일정 체크리스트

- 정책별 예시 서류와 최대 세 개의 체크 항목을 표시한다.
- 체크리스트 상태를 PostgreSQL에 저장하며 멱등 키 기준 중복 항목을 방지한다.
- 일반 이사 안내는 전입신고·확정일자·보증보험 등 최대 세 항목의 예시로 제한하며 개인별 법정 기한을 단정하지 않는다.

### FR-03 지원: 장애 탐지·복구·검증 기록

- 네 가지 장애를 탐지하고 incident/trace ID, 시각, 근거, 진단, 시도, 회로, 검증, 최종 상태를 기록한다.
- 재시도·차단·half-open은 고정 설정으로 통제한다.
- 복구 담당자와 독립된 검증에서 증거가 확인된 경우에만 `RECOVERED`로 종료한다.
- 실패 또는 상태 불명은 `SAFE_STOP`/`ESCALATED`로 종결하고 사용자에게 수동 확인 경로를 제공한다.

## 14. 비기능 요구사항

- **안전성:** 모든 동작은 최소 권한·allowlist 기반이다. Unknown·검증 불가·상태 불명에서는 안전 중단한다.
- **신뢰성:** 최초 포함 최대 4회, 고정 백오프 상한, 20초 회로 냉각, half-open 1회로 무한 루프를 막는다.
- **멱등성:** 일정 쓰기는 복합 멱등 키로 중복을 억제하고, 저장 상태 불명일 때는 추가 쓰기를 금한다.
- **검증 가능성:** 장애 주입에서 종료까지의 시각과 근거를 사건 타임라인으로 재구성할 수 있어야 한다.
- **개인정보 최소화:** 합성 데이터만 쓴다. 정확한 소득액, 계약서 원문, 계정·인증정보, 모델 비공개 추론은 저장하지 않는다.
- **설명 가능성:** 결과에 공식 출처, 기준일, 규칙 버전, 근거 코드가 연결되어야 한다.
- **접근성:** 결과 상태와 다음 행동은 쉬운 한국어로 표시한다.
- **성능 목표:** 일반 장애 시연에서 MTTD ≤5초 및 MTTR ≤15초를 목표로 한다. 전체 워크플로는 30초, 각 역할 호출은 3초로 제한한다. 회로 차단 시나리오는 요청을 먼저 안전 종료하고 20초 냉각 후 별도 half-open 결과를 기록한다. 전체 사용자 응답 SLA는 보장하지 않고 측정만 한다.

## 15. 데이터·로그·저장

| 데이터 | 저장 위치 | 규칙 |
|---|---|---|
| 정책 사례·출처·기준일 | 로컬 JSON | 읽기 전용, 출처 URL·기준일 필수, 운영 중 자동 수정 금지 |
| 사건·시도·검증 타임라인 | PostgreSQL | incident_id, trace_id, 시각, 관측 근거, 결과 코드, 재시도 번호, 회로 상태, 검증 상태를 기록 |
| 체크리스트 상태 | PostgreSQL | 합성 시나리오 ID와 멱등 키만 저장; 동일 키당 한 항목 |
| 합성 프로필 | 메모리/가상 테스트 fixture | 실제 개인과 연결하지 않으며 원시 개인정보를 로그에 남기지 않음 |

타임스탬프는 ISO 8601 UTC로 저장한다. 사건 로그는 생성 시점부터 30일 보존하고 이후 삭제 대상으로 처리한다. 이 보존 정책은 합성 실습 데이터에 적용한다. 연결 실패로 타임라인 기록도 불가능하면 로컬 응답에 `저장 확인 불가`를 표시하고, 장애를 성공으로 숨기지 않는다. LLM에는 DB 접속정보와 쓰기 권한을 주지 않는다.

## 16. 독립 복구 검증과 완료 판정

Verification은 Recovery가 반환한 성공 문자열만 신뢰하지 않고 다음을 독립적으로 읽는다.

1. 대상 의존 기능 헬스체크가 응답하는가?
2. 정책 검색이면 정책 수·기준일·공식 URL과 결과 스키마가 유효한가?
3. 일정 저장이면 멱등 키별 항목이 정확히 하나이며 상태가 조회되는가?
4. DB 저장이면 사건·체크리스트 상태를 읽어 확인할 수 있는가?
5. 복구 결과가 시도 상한·회로 상태·권한 경계를 지켰는가?

모든 관련 확인이 통과할 때만 복구 성공으로 기록한다. 검증 실패, 누락, 타임아웃, DB 조회 불가 또는 결과 충돌은 실패/상태 불명으로 처리하고 재시도 상한·회로·에스컬레이션 규칙을 적용한다. 최종 사용자 안내에는 결과, 근거, 기준일, 공식 링크 및 필요한 수동 행동을 포함한다.

## 17. MVP 범위와 일정

### 포함

- 서울 청년 주거지원 예시 정책 3개와 공식 출처 링크
- 합성 프로필 1개, 규칙 기반 비교, 정보 부족 상태
- 최대 3개 체크리스트 항목과 PostgreSQL 상태 저장
- 네 장애 주입기, 제한 복구, 회로 차단, 독립 검증, 사건 타임라인
- 실패 시 안전 중단과 사람 확인 안내

### 제외

- 실제 사용자 계정, 개인정보·계약서 처리, 외부 API 신청/제출 및 알림
- 실제 운영 복구, 자동 정책 업데이트, 전 자치구·전 제도 데이터
- 고급 추천/자율 에이전트의 정책 판단, 법률·자격 확정

### 3일 계획

- Day 1: 요구사항·아키텍처·승인된 작업목록 확정
- Day 2: 모의 정책/일정 기능, 결정 규칙, 저장 및 사건 오케스트레이션 구현
- Day 3: 네 장애 시나리오 재현, 독립 검증, 지표·데모 결과 정리

작업목록은 PRD 승인 이후 `prompts/02-generate-tasks.md` 절차로 별도 생성·승인한다.
