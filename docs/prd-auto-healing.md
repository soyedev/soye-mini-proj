## 1. 서비스와 사용자 문제

### 서비스 정의

서울 거주 청년이 가상 사용자 조건과 이사 예정일을 입력하면, 서비스는 일부 중앙정부·서울시 공통 주거 지원제도를 비교하고 필요한 서류와 일정을 안내한다.

- 주요 사용자: 서울에서 이사를 준비하는 청년
- 입력: 서울 거주 여부(실습에서는 서울로 고정), 나이, 소득 구간, 가구 형태, 이사 예정일
- 입력하지 않음: 실제 소득액, 임대차계약서 파일 또는 계약서 원문
- 결과: 지원 가능성 안내, 정보 부족 또는 조건 불일치 상태, 필요한 서류와 일정, 공식 출처 링크
- 실제 자격 확정 및 신청 대행: MVP 범위 밖

### 정상 서비스 흐름

가상 프로필과 이사 예정일 입력
→ 모의 정책 검색
→ 정책 조건 비교
→ 서류 목록 및 일정 안내
→ 공식 출처·신청 페이지 링크 표시

### 핵심 의존 기능

| 의존 기능 | 용도 | 실패 시 사용자 영향 | 실습 방식 |
|---|---|---|---|
| 정책 검색 기능 | 예시 정책 3개를 검색하고 비교 자료 반환 | 제도 비교 결과가 지연되거나 표시되지 않음 | 모의 기능 |
| 일정·알림 기능 | 서류·신청 일정 및 제한된 이사 체크 항목 표시 | 일정 안내가 지연되거나 표시되지 않음 | 모의 기능 |

### 서비스 중단 영향

- 사용자 영향: 정책 비교 또는 서류·일정 안내를 받을 수 없으며, 복구 실패 시 공식 페이지에서 직접 확인해야 한다.
- 운영 영향: 장애 유형, 근거, 시도 내역과 검증 결과를 확인해야 한다.
- 데이터·보안 영향: 가상 프로필만 사용한다. 원문 소득이나 계약서는 받지 않고 로그에도 남기지 않는다.
- 심각도: 중간. 안내 기능은 중단되지만 실제 신청·결제·운영 데이터 처리는 하지 않는다.
- 기존 운영 대응 경험: 운영 중인 서비스가 아니므로 [미결정/해당 없음]. 실습 장애는 모의 신호로 감지한다.

## 2. MVP와 장애 시나리오

### MVP 포함

- 예시 정책 3개의 비교와 기준일·접수 상태·출처 표시
- 가상 프로필에 대한 가능성 안내 및 정보 부족 상태 표시
- 제도별 서류·신청 일정 안내
- 일반 이사 체크 항목은 최대 3개 예시로 제한: 전입신고, 확정일자, 보증보험
- 일반 이사 항목은 공식 링크를 제공하며 개인별 법정 기한을 계산하거나 법률 판단을 하지 않음
- 세 가지 의존 기능 장애의 탐지·제한 복구·독립 검증·실패 안내

### MVP 제외

- 자치구별 제도와 모든 주거지원 제도의 망라
- 실제 개인정보 및 계약서 업로드·분석
- 실제 정부 API 신청·제출, 실제 외부 알림 발송
- 확정적인 자격 판정, 법률 자문, 신청 대행
- 임의 쉘 명령 실행이나 허용되지 않은 서비스 조작

### 안전하게 재현할 장애

| 장애 | 발생 위치 | 탐지 신호 | 사용자 영향 | 안전한 재현 방법 | 예상 복구 방향 |
|---|---|---|---|---|---|
| HTTP 5xx | 모의 정책 검색 | 서버 오류 응답 | 정책 비교 결과를 받지 못함 | 실습용 검색 기능이 오류 응답을 반환하도록 설정 | 제한된 재시도, 독립 확인, 실패 시 공식 링크 안내 |
| 응답 시간 초과 | 모의 정책 검색 | 응답 제한 시간 초과 | 비교 결과가 지연됨 | 실습용 검색 응답을 지연시킴 | 제한된 재시도, 독립 확인, 실패 시 공식 링크 안내 |
| 연결 실패·기능 중단 | 모의 일정·알림 | 연결 실패 또는 일정 결과 부재 | 일정 안내가 누락됨 | 실습용 일정 기능을 실패 상태로 설정 | 제한된 재시도, 멱등 확인, 실패 시 수동 체크리스트 안내 |

같은 정책 검색 사건이 재시도 상한까지 실패하는 경우는 별도의 장애 종류가 아니라 회로 차단 동작을 확인하는 반복 시나리오로 사용한다.

## 3. 에이전트 역할과 판단 경계

역할은 책임 단위로 정의한다. 별도 LLM 에이전트로 구현할지는 정하지 않는다. 복구와 검증은 독립된 역할로 유지한다.

| 역할 | 책임·입력·출력 | 에이전트 판단 | 고정 규칙 | 권한·금지 행동·실패 처리 |
|---|---|---|---|---|
| Monitor | 의존 기능의 상태를 관찰하고 사건 신호를 출력 | 없음 | 사전 정의한 오류·타임아웃 신호로 사건 생성 | 읽기와 사건 기록만 허용; 복구 실행 금지; 감시 실패 시 자동 복구를 시작하지 않고 알림 |
| Diagnosis | 오류 신호와 사건 근거를 받아 허용된 장애 유형 후보와 근거 참조를 출력 | 최종 장애 분류나 복구 행동을 결정하지 않음 | 고정 신호 매핑 규칙으로 최종 분류; 근거 누락·충돌·미등록 유형은 Unknown | 복구 직접 실행 금지; Unknown은 자동 변경 없이 에스컬레이션 |
| Recovery | Orchestrator가 승인한 복구 작업 ID와 사건 정보를 받아 결과 출력 | 판단·전략 생성 없음 | 허용목록, 횟수 상한, 대기시간, 회로 상태를 고정 규칙으로 적용 | 모의 기능만 호출; 임의 명령·실제 신청·정책 변경·DB 직접 접근 금지; 조건 불일치 시 중단 |
| Verification | 복구 결과와 독립 상태를 확인해 성공·실패 출력 | 성공을 자체 판단으로 선언하지 않음 | 헬스체크와 기대 결과 항목을 별도로 확인 | 읽기 전용 확인; 실패하면 사건을 종료하지 않고 사용자 안내 |
| Orchestrator | 사건 상태, 호출 순서, 시도 상한, 회로 상태 관리 | 임의 계획 수립 없음 | 고정 상태 흐름과 한도 적용 | 정책 우회 및 검증 생략 금지; 상태가 불명확하면 중단·에스컬레이션 |
| Notification | 최종 상태와 공식 출처를 사용자에게 전달 | 정책 자격을 해석하거나 확정하지 않음 | 승인된 문구와 링크로 안내 | 복구 정책 변경 금지; 알림 실패는 기록하고 수동 확인 경로 제공 |

서비스 기능의 판단 방식:

| 기능 | 처리 방식 | 경계 |
|---|---|---|
| 정책 검색·조건 비교 | 예시 정책의 출처에 기록된 기준을 적용하는 고정 규칙 | 자격 확정 대신 가능성·정보 부족·조건 불일치 상태만 반환 |
| 서류·일정 생성 | 정책에 등록된 서류·일정 정보와 고정 체크 규칙 | 미등록 조건이나 개인별 법정 기한을 만들어내지 않음 |
| 장애 원인 설명 | Diagnosis 역할이 관찰 근거를 설명하고 알려진 범주 중 후보를 제시 | 불확실하거나 알려지지 않은 장애는 자동 변경 없이 사람에게 전달 |
| 재시도·회로 차단·중복 방지·검증 | 고정 규칙 | 모델 생성 판단에 맡기지 않음 |

### AI가 독자적으로 결정·실행하지 못하게 하는 통제

- **자격 판단:** AI가 지원 자격을 확정하거나 임계값·마감일·정책 조건을 만들어내지 않는다. 출처와 버전이 기록된 모의 정책 자료에 고정 규칙을 적용하고, 근거가 없거나 서로 충돌하면 `정보 부족`으로 반환한다.
- **장애 진단:** AI는 사전 정의된 장애 유형 중 후보와 근거만 제시할 수 있다. 최종 유형은 고정 규칙이 정하며, 매핑되지 않거나 불확실하면 `Unknown`으로 안전 중단한다.
- **복구 결정:** AI가 복구 전략, 재시도 횟수, 대기시간, 회로 차단 기준을 바꾸거나 새 행동을 만들 수 없다. Orchestrator는 상태 기계와 허용목록에 등록된 작업만 실행한다.
- **도구 권한:** AI 역할에는 쉘, SQL 실행, PostgreSQL 직접 쓰기, 정부 사이트 조작, 실제 알림 발송 권한을 주지 않는다. 모든 상태 변경은 검증된 입력을 받는 애플리케이션의 고정 기능을 통해서만 수행한다.
- **출력 검증:** 모델 출력은 정해진 필드·허용값·식별자 참조를 검사한다. 형식이 틀리거나 허용되지 않은 값이면 버리고, 행동으로 변환하지 않는다.
- **외부 자료:** 검색 결과와 정책 문서는 신뢰할 수 없는 데이터로 취급한다. 그 안에 포함된 지시문은 실행 지시로 따르지 않는다. 사용자 안내는 검증된 정책 근거와 승인된 문구만 사용한다.
- **승인 경계:** 새 정책·규칙·복구 작업·허용목록 변경, 실제 외부 서비스 호출은 자동 반영하지 않는다. Unknown, 근거 충돌, 상태 확인 실패는 사람에게 전달한다.
- **독립 검증:** Recovery의 성공 보고만으로 사건을 종료하지 않는다. 읽기 전용 Verification이 별도 기준을 확인하고, 실패 또는 확인 불가면 성공으로 표시하지 않는다.

## 4. 자율성, 복구 및 중복 통제

### 자동 실행 가능

- 모의 정책 검색·일정 기능에 대한 사건당 제한 재시도
- 회로가 열린 동안 해당 의존 기능의 자동 호출 중단
- 냉각 후 half-open 헬스체크 1회
- 같은 멱등 키의 일정 항목 재사용 또는 갱신
- 복구 이후 독립 검증과 사건 기록

### 사람 승인 후 실행

- 실제 정책 자료의 내용 변경 또는 운영 데이터 변경
- 향후 실제 외부 서비스 연동·신청처럼 사용자 또는 운영자에게 영향을 주는 행동
- 이 항목들은 MVP에 포함하지 않는다. 추가하려면 별도 승인과 범위 검토가 필요하다.

### 자동 실행 금지

- 임의 쉘 명령 생성·실행
- 실제 개인정보·계약서 변경 또는 저장
- 실제 정부 사이트 조작·신청 제출·실제 알림 발송
- 근거 없는 자격 확정 및 알려지지 않은 장애의 자동 변경

### 재시도와 대기

- 재시도 한도: 의존 기능별 사건당 추가 재시도 3회. 최초 호출을 포함해 같은 사건에서 최대 4회 호출한다.
- 대기 방식: 지수형으로 늘리는 대기와 무작위 지연을 적용한다.
- 명목 대기 간격: 1초, 2.5초, 5초. 각 간격에 ±20% 지터를 적용한다.
- 입력 오류 등 재시도로 해결되지 않는 오류는 재시도하지 않는다.
- 시도 횟수는 사건 기록에 남기고 PostgreSQL에 저장한다. 시도 상한과 대기시간은 모델이 변경할 수 없다.

### 회로 차단과 재개

- 범위: 정책 검색과 일정 기능 각각 독립된 회로를 사용한다.
- 차단 조건: 동일 의존 기능의 동일 사건에서 최초 요청과 재시도 3회가 모두 실패한 경우 연다. 서로 다른 사건이나 다른 기능의 오류를 합산하지 않는다.
- 열린 동안: 해당 의존 기능의 새 자동 호출을 멈추고 사용자에게 장애 상태와 공식 확인 링크를 안내한다.
- 냉각시간: 20초. 실습 시연 값이며 실제 운영 환경에서 조정 가능하다.
- half-open: 20초 후 상태 확인 요청 1회만 허용한다. 성공하면 닫고, 실패하면 다시 열린 상태로 두고 에스컬레이션한다.

### 중복 및 안전 중단

- 멱등 키: 가상 시나리오 + 정책 + 일정 종류 + 예정일 조합으로 식별한다.
- 재시도 시 새 항목을 추가하지 않고 같은 키의 항목을 재사용하거나 갱신한다.
- 검증 기준: 키별로 일정 항목이 정확히 하나인지 확인한다.
- 기존 상태를 확인할 수 없으면 추가 실행을 멈추고 실패 안내를 한다. 임의 삭제로 중복을 정리하지 않는다.
- 정책 검색은 읽기 전용이므로 롤백 대상이 없다. 일정 상태가 불명확한 경우 안전 중단과 안내를 사용한다.

## 5. 검증과 추적 기록

### 복구 성공 기준

- 정상 요청에서 정책 예시 3개와 각 자료 기준일·접수 상태·공식 출처를 표시한다.
- 가상 프로필에서 가능성 안내, 정보 부족 또는 조건 불일치 상태 중 하나를 표시한다.
- 이사 예정일을 바탕으로 제도별 서류·일정과 최대 3개의 일반 이사 체크 항목을 표시한다.
- 세 장애 유형 각각에 대해 탐지 기록이 남고, 복구 후 독립 검증을 통과하거나 상한 내 실패 후 안전하게 안내한다.
- 반복 실패 시 동일 사건 기준으로 회로가 열리고, 20초 후 half-open 검사 결과가 기록된다.
- 일정 안내의 재시도 후 멱등 키별 항목이 하나만 남는다.

수치형 응답 SLA는 [미결정]. MTTD와 MTTR은 측정해 기록하되, 별도 수치 목표는 [미결정]이다.

### 사건 타임라인과 필수 기록

사건별 시간순 타임라인으로 기록한다. 각 기록은 다음 정보를 포함한다.

- 사건 식별자와 추적 식별자
- 장애 주입·탐지·복구 시작·검증 또는 에스컬레이션 시각
- 장애 신호와 진단 근거
- 시도 번호, 대기시간, 회로 상태 전이
- 검증 결과, 사용자 안내 여부, 최종 상태

사건 타임라인과 생성된 이사 체크리스트의 상태는 PostgreSQL에 저장해 화면을 다시 열어도 확인할 수 있게 한다. 모의 정책 자료는 출처·기준일이 포함된 읽기 전용 JSON 자료로 둔다. 실제 사용자 프로필, 정확한 소득액, 계약서 원문, 인증정보와 모델의 비공개 추론 내용은 저장하지 않는다.

AI 역할은 PostgreSQL에 직접 연결하지 않으며 SQL을 만들거나 실행하지 않는다. 저장·수정은 애플리케이션의 고정 기능만 담당한다. 저장 성공 여부나 기존 멱등 상태를 확인할 수 없으면 저장됐다고 안내하거나 같은 항목을 다시 만들지 않고, 해당 흐름을 안전하게 멈춘 뒤 알린다.

## 7. 범위 및 검토 상태

- 팀은 1인이다. Python 학습 경험과 Docker·DB·워크플로 사용 경험이 있다. JSON 경험은 확실하지 않다.
- PostgreSQL은 사건 타임라인과 이사 체크리스트 상태를 저장하는 기술로 확정했다. 모의 정책 자료는 읽기 전용 JSON으로 둔다. 그 외 구체 기술 선택은 확인된 교육환경 제약이 아니므로 PRD에서 고정하지 않는다.
- 서비스 선정은 사용자가 승인했다. 워크시트와 PRD의 최종 검토·승인은 아직 받지 않았다.
- PRD 초안은 핵심 미결정 사항 확인 후 작성한다.
- 작업목록, 코드, 테스트, 배포 파일, 실제 장애 주입은 현재 범위에서 작성·실행하지 않는다.
